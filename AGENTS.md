# AGENTS.md - Developer & Agent Guidelines for Ryuk

## 1. Project Overview
**Ryuk** is a developer-first, minimal personal knowledge operating system built as a modern TypeScript monorepo. It enables users to store, organize, and manage bookmarks, metadata, and knowledge assets.

The repository is structured as a **pnpm + Turborepo monorepo** containing a Next.js 16 web application (`apps/web`), planned CLI tools (`apps/cli`), and modular internal packages for database management (`@ryuk/db`), authentication (`@ryuk/auth`), shared UI (`@repo/ui`), and workspace tooling configurations (`@repo/eslint-config`, `@repo/typescript-config`).

## 4. Development Commands

### Monorepo Root Commands (pnpm + Turbo)
- **`pnpm dev`**: Start development servers across all monorepo apps concurrently via Turbo (`turbo run dev`).
- **`pnpm build`**: Build production assets across all packages (`turbo run build`).
- **`pnpm lint`**: Run ESLint across all apps and packages (`turbo run lint`). Enforces zero warnings (`--max-warnings 0`).
- **`pnpm check-types`**: Run TypeScript type checking (`tsc --noEmit`) across all monorepo workspace packages (`turbo run check-types`).
- **`pnpm format`**: Format all TypeScript, TSX, and Markdown files across the codebase using Prettier (`prettier --write "**/*.{ts,tsx,md}"`).

### Package-Specific Filtering Commands
- **`pnpm --filter web dev`**: Run only the Next.js web application dev server.
- **`pnpm --filter web check-types`**: Run type check for `apps/web` only.
- **`pnpm --filter web lint`**: Run ESLint for `apps/web` only.
- **`pnpm --filter @ryuk/db db:generate`**: Generate Drizzle database migrations.
- **`pnpm --filter @ryuk/db db:push`**: Push schema changes directly to PostgreSQL database.
- **`pnpm --filter @ryuk/db db:studio`**: Open Drizzle Studio database UI.

## 5. Authentication Rules

1. **Architecture**: Authentication is centralized in `@ryuk/auth` using `@supabase/ssr`.
2. **Client vs. Server Instantiation**:
   - **Client Components**: Always import `createBrowserSupabaseClient` from `@ryuk/auth/client`. Do NOT instantiate Supabase directly or import from `@ryuk/auth/server`.
   - **Server Components & Server Actions**: Always import `createServerSupabaseClient` or `getUser` from `@ryuk/auth/server`.
3. **Session Retrieval**:
   - Prefer calling `getUser()` from `@ryuk/auth/server` over `getSession()` in server contexts for secure authentication checks.
4. **Route Protection**:
   - Protect dashboard routes at the Server Component page level (or middleware when implemented) using:
     ```ts
     const user = await getUser();
     if (!user) redirect("/login");
     ```
5. **OAuth Flow**:
   - OAuth redirect URLs must point to `${window.location.origin}/auth/callback`.
   - The `/auth/callback` route handler exchanges the temporary auth code for a session using `exchangeCodeForSession(code)`.

---

## 6. Client and Server Component Rules

1. **Default Server Components**: All components and pages in Next.js App Router (`apps/web/app`) are **Server Components** by default. Keep components as Server Components unless interactivity is strictly required.
2. **Client Component Boundaries**:
   - Place `"use client";` at the very top of files requiring React state (`useState`, `useRef`), event handlers, browser-only APIs, or React Query hooks (`useQuery`, `useMutation`).
   - Keep Client Component boundaries as granular as possible (e.g., wrap individual interactive forms like `BookmarkForm` instead of making an entire page a Client Component).
3. **Server Action Declarations**:
   - Always add `"use server";` at the top of Server Action files (e.g., `src/features/bookmarks/actions/index.ts`).
   - Server Actions must validate incoming input using Zod before performing database mutations.
4. **Import Separation**:
   - **NEVER** import server-only modules (`@ryuk/auth/server`, `@ryuk/db`, `next/headers`, `postgres`, `drizzle-orm`) inside Client Components.

## 7. Supabase Usage Rules

1. **Environment Variables**:
   - Require `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (or `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`).
   - Fallback placeholder values exist in `@ryuk/auth` to prevent crash on startup, but valid credentials are required for actual authentication.
2. **Cookie Handling**:
   - Cookie manipulation is handled automatically in `createServerSupabaseClient` via `cookies()` from `next/headers`.
   - Ensure `setAll` cookie modification exceptions in `server.ts` are caught gracefully when rendered in pure Server Component contexts.
3. **Database RLS**:
   - Database operations executed through Drizzle or Supabase MUST always scope user data by `user.id`.

## 8. React Query Rules

1. **Global Provider**:
   - `<QueryProvider>` in `src/providers/query-provider.tsx` wraps the application root in `apps/web/app/layout.tsx`.
   - Initialize `QueryClient` inside React `useState` to prevent state leakage across request contexts during Server Side Rendering.
2. **Custom Hook Encapsulation**:
   - Co-locate React Query logic inside `hooks/` within each feature directory (e.g., `src/features/bookmarks/hooks/use-bookmarks.ts`).
3. **Query Keys**:
   - Define query keys as explicit `as const` array tuples (e.g., `export const BOOKMARKS_KEY = ["bookmarks"] as const;`).
4. **Cache Invalidation**:
   - Invalidate query caches upon successful mutations using `queryClient.invalidateQueries({ queryKey: BOOKMARKS_KEY })`.
5. **Server Action Integration**:
   - Wrap Server Action calls inside `queryFn` for queries and `mutationFn` for mutations. Throw typed errors when action responses contain `{ error }`.

## 9. Navigation Rules for Next.js

1. **App Router Structure**:
   - Route groups are denoted with parentheses: `(auth)`, `(dashboard)`, `(site)`.
   - Static/Public pages reside in `(site)` or `(auth)`. Authenticated routes reside in `(dashboard)`.
2. **Client Navigation**:
   - Use `<Link href="...">` from `next/link` for declarative navigation.
   - Use `useRouter()` from `next/navigation` in Client Components for programmatic navigation (e.g., `router.push("/dashboard")`, `router.refresh()`).
3. **Server Navigation**:
   - Use `redirect("/path")` from `next/navigation` in Server Components and Server Actions.
4. **Cache & Path Revalidation**:
   - Call `revalidatePath("/path")` inside Server Actions after data mutations to refresh Next.js route caches.

## 10. Validation and Error-Handling Rules

1. **Zod Validation**:
   - Define input validation schemas inside feature `schemas/` directories (e.g., `src/features/bookmarks/schemas/index.ts`).
   - Always parse raw inputs with `schema.safeParse()`.
2. **Safe Array Access**:
   - Under strict TypeScript rules (`noUncheckedIndexedAccess` or strict null checks), accessing Zod error issues via `parsed.error.issues[0]` requires bounds checking or optional chaining:
     ```ts
     const message = parsed.error.issues[0]?.message ?? "Invalid input";
     ```
3. **Action Error Contracts**:
   - Server Actions should return unified response shapes: `{ data: T }` or `{ error: string }`.
   - Avoid throwing raw unhandled exceptions from Server Actions to the client.
4. **Scraping Fallbacks**:
   - Web metadata scraping (`scrapeUrlMetadata`) must swallow network failures gracefully and return basic hostname fallback favicons instead of failing.

## 11. Security Rules

1. **Authentication Enforcement**:
   - Verify `getUser()` in every Server Action before processing data or querying database records.
2. **Database Data Isolation**:
   - Always scope database queries by `userId` (e.g., `.where(eq(bookmarks.userId, user.id))`).
3. **Environment Security**:
   - Keep `DATABASE_URL` strictly on the server (`packages/db`). Never expose database connection strings or service role keys with `NEXT_PUBLIC_` prefixes.
4. **API Key Storage**:
   - `api_keys` table stores salted/hashed keys (`key_hash`) and hints (`key_hint`). Never store raw API keys in the database.
5. **External Link Safety**:
   - External anchor tags MUST include `target="_blank"` and `rel="noreferrer"` attributes (see `BookmarkCard`).

# 2. Run lint checks across all packages (must pass with 0 warnings)

## 15. Rules to Preserve Unrelated Local Changes

1. **Respect Working Tree State**:
   - Do NOT modify, revert, or discard existing unstaged modifications or deleted files in git unless explicitly instructed by the user.
   - Current modified/deleted files in working tree (such as deleted `apps/docs/` files, modified `package.json`, `tsconfig.json`, `layout.tsx`, `globals.css`) must be preserved intact.
2. **Scope of Modification**:
   - Only edit or create files requested by the user. For this task, only `AGENTS.md` may be created or updated.
3. **No Side Effects**:
   - Do NOT install new pnpm packages.
   - Do NOT delete or rename any workspace files or folders.
   - Do NOT mutate application logic when performing environment inspections.
